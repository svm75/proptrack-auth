## 11. Migration Options

| Option | Fit for this migration |
|---|---|
| Manual Web API GET export (paged, script-driven) | Straightforward for ~1,341 rows across 14 tables; full control over choice-code and lookup-GUID mapping; no extra tooling; slower to hand-roll pagination/retry logic than a purpose-built tool |
| `pac org fetch` (FetchXML) scripted per table | Already proven working in this session (used for counts/dates); returns tabular text, would need parsing/reshaping into insertable rows; no native paging beyond FetchXML's own `page`/cookie mechanism |
| Power Query / Excel export | Good for spot-checks and the user's own review, not suited to a scripted, repeatable, GUID-preserving bulk load |
| Data Export Service | **Deprecated by Microsoft** — not viable for a new migration |
| Azure Synapse Link | Massive overkill for ~1,341 rows across 14 tables; introduces an Azure Synapse/Data Lake dependency purely to move a small dataset; not proportionate |
| `pac data export` (data package /solution-based export) | Designed for solution-packaged, managed data migrations between Dataverse environments, not for exporting into a foreign format like Postgres rows; would still require a transform step afterward |
| Third-party ETL (e.g. a script using `@microsoft/power-apps`/`dataverse-webapi` or a generic ETL tool) | Viable, but adds a dependency; the app's own generated `src/generated/services/` already wrap Web API calls with correct typing — closest thing to already-built tooling |

## 12. Recommended Migration Method

**A custom one-time export script using the Dataverse Web API (OData v9.2, GET-only) driven off the already-generated TypeScript types in `src/generated/`**, table-by-table in the dependency order from §8, writing normalized rows (or JSONB, pending the §15 decision) into PostgreSQL with:
- Dataverse GUIDs preserved as the row identifiers (or mapped 1:1 to new UUIDs with a translation table, if the target schema's convention — TripOrganiser-style — expects UUIDs distinct from Dataverse GUIDs; note Dataverse GUIDs already print as standard UUID-formatted strings, so a straight reuse is likely simplest).
- Choice/option-set integer codes preserved as-is, or translated to the human labels/CHECK-constrained text using the mappings already fully documented in `docs/schema.md` and `src/domain/types.ts` — do not re-derive them from scratch.
- Lookup GUIDs resolved to FK references only after parent tables are loaded, per the §8 dependency order.
This is proportionate to a **~1,341-row, GB-scale-in-name-only** dataset (well under 1 GB of actual data even accounting for text fields), avoids Synapse/DES overkill, and reuses tooling the app already has (`src/generated/services/`) rather than hand-rolling raw HTTP auth. It also matches the precedent already set by both sibling repos (`wealth-ledger`, `TripOrganiser`), which each did a similar Dataverse→Postgres one-time export rather than adopting Synapse/DES.

## Choice Mapping

**Strategy**: every Dataverse Choice/OptionSet column is preserved as its **raw numeric source code**, stored as `SMALLINT`, with a **table-scoped** `CHECK` constraint (never a shared/global Postgres `ENUM` type spanning tables). This is deliberate, not an oversight: `Invoices.type`, `ForecastFlows.type`, and `InvoiceTemplates.type` use three mutually incompatible numeric ranges for "Income"/"Expense" —

| Table.column | Income | Expense |
|---|---|---|
| `invoices.type` | 233100001 | 233100000 |
| `forecast_flows.type` | 233100000 | 233100001 |
| `invoice_templates.type` | 925060000 | 925060001 |

— and a single shared enum/lookup would force normalizing these onto one value space, which is exactly the trap §B warns against. Keeping each column's own raw code, CHECK-scoped to its own table, keeps the migration a pure identity mapping: deterministic (no relabeling function to derive) and trivially reversible (round-trips exactly, byte-for-byte, back to the Dataverse option value). Human-readable labels belong at the API/domain layer, mirroring `src/domain/types.ts`'s existing `as const` maps — those maps are reused unchanged as the label layer, not re-derived.

All 20 lookups from §8 are translated to PostgreSQL foreign keys in `db/001_schema.sql`; full detail (nullability, ON DELETE) is inline there. Summary:

| Table.column | → Target | ON DELETE | Rationale |
|---|---|---|---|
| `contacts.default_category_id` | `reference_data` | SET NULL | Category is a soft default, not structural |
| `supplier_contracts.contact_id` | `contacts` | RESTRICT | Preserve billing history integrity |
| `supplier_contracts.property_id` | `properties` | RESTRICT | Same — contracts are historical/operational records |

| `invoice_comments.invoice_id` | `invoices` | CASCADE | A comment has no meaning detached from its invoice; invoices are never hard-deleted in practice (soft delete via `is_cancelled`), so this CASCADE never actually fires against real financial history |
| `invoice_templates.category_id` | `reference_data` | SET NULL | Templates are conveniences, not history |
| `attachments.invoice_id` / `.property_id` | `invoices` / `properties` | CASCADE | Attachment rows are pure metadata pointers to Google Drive files; deleting the parent record's Drive folder makes the pointer meaningless too. (0 live rows today — low risk either way, chosen for symmetry with `invoice_comments`.) |
| `attachments.property_id_invoice` | `properties` | SET NULL | Unused-by-app field; preserved, not treated as structural |
| `attachments.contact_id` / `.attach_type_id` | `contacts` / `reference_data` | SET NULL | Optional context fields |
| `forecast_flows.category_id` / `.contact_id` | `reference_data` / `contacts` | SET NULL | Forecasts are planning data, not realized financial history |
| `forecast_flows.parent_flow_id` | `forecast_flows` (self) | SET NULL | Deleting a superseding version should not delete or block deleting its predecessor; a `CHECK (parent_flow_id IS DISTINCT FROM id)` blocks a flow from pointing at itself |
| `forecast_flow_properties.forecast_flow_id` / `.property_id` | `forecast_flows` / `properties` | CASCADE | Pure junction row, meaningless once either side is gone |
| `forecast_scenarios.property_id` | `properties` | CASCADE | Scenario is scoped to (and meaningless without) its property; NULL = portfolio-wide, unaffected |

`UNIQUE` constraints: `properties.short_id` (mirrors the Dataverse alternate key `svm_shortid`). `invoices.internal_id` is deliberately **not** unique-constrained — the source system never enforced this server-side either (`docs/schema.md` quirk #7); adding it now could reject migrated data that already contains duplicates, a behavior change outside this step's scope.

## Reconciliation Strategy

Fully automated, run immediately after each table load and again after the full migration — no manual sampling, per instruction:

1. **Row-count reconciliation**: for every one of the 14 tables, the load script runs `SOURCE COUNT` (the same aggregate FetchXML pattern already used in §7) against Dataverse and `SELECT count(*) FROM proptrack.<table>` against Postgres, and emits one row per table: `table | source_count | target_count | difference`. The script exits non-zero if any `difference <> 0`. Expected result: all differences 0, total 1,341.
2. **Row-level checksum reconciliation** (stronger than count-only): for every migrated row, compute a deterministic hash (e.g. SHA-256) over a canonical concatenation of its column values on both the Dataverse-side export and the Postgres-side row (by shared `id`), and diff the two hash sets. Reports any `id` present in one side but not the other (missing/orphaned) and any `id` present in both with a differing hash (value drift), not just a raw count that could hide a swap.
3. **FK integrity verification**: a single automated query per FK, generated from the table in §Foreign Keys and Constraints, of the form `SELECT count(*) FROM <child> WHERE <fk_col> IS NOT NULL AND <fk_col> NOT IN (SELECT id FROM <parent>)` — must return 0 for every one of the 20 FKs. This also implicitly re-validates the §Migration Load Order dependency ordering (an orphan here means a child was loaded before its parent, or a GUID was mistranscribed).
4. **Choice/domain reconciliation**: for every CHECK-constrained column in §Choice Mapping, a query confirming every non-NULL value in Postgres falls within the documented code set for that column (catches an option-set value that existed live in Dataverse but wasn't in the discovered enumeration — the same class of gap §7/§15 already found once for `reference_data.reference_type` and `activity_logs.table_name`).
5. **Known-anomaly assertion**: an explicit check that exactly 2 rows in `invoices` have `is_flagged_anomaly = true` and `EXTRACT(year FROM invoice_date) = 1962` — turns the one known, accepted data anomaly into a passing assertion rather than a silent discrepancy that would otherwise show up as a false failure in step 2's checksum diff (it won't, since the rows are migrated byte-for-byte, but this assertion documents the anomaly is *expected*, not newly introduced).

All five checks run as one script/report, producing a single pass/fail reconciliation summary — this is the acceptance gate for Step 3's Action 6 in §16 below (unchanged from the original 9-step plan).

## API Architecture

**Minimum Node/TypeScript API** in front of PostgreSQL, replacing `src/generated/services/*` one-for-one at the call-site level so `src/domain/` and the screens stay largely unchanged:

- **Repository/data-access structure**: one repository module per table (`propertiesRepo.ts`, `invoicesRepo.ts`, …), each exposing typed CRUD + the table's specific queries (e.g. `invoicesRepo.nextSequence(propertyId, year)`), mirroring the shape `src/generated/services/*Service.ts` already has today — this keeps the swap mechanical rather than a rewrite. A thin `db.ts` wraps a `pg` (`node-postgres`) `Pool` (see connection management below).
- **Endpoints/service operations**: a REST (or tRPC, either is proportionate at this scale) surface with one resource per table plus a small number of composite/read endpoints for screens that currently do client-side joins across the generated services — e.g. `GET /forecast-flows/:id/resolved` (§Business Rule Placement), `GET /invoices/next-internal-id?propertyId=&year=`, `GET /properties/:id/deletable` (usage-count check), `GET /reference-data/:id/usage-count`. Every existing screen operation in §9/§14 maps to one of: a plain CRUD call, one of these composite endpoints, or a client-side `src/domain/` calculation over data the CRUD calls already returned (unchanged).
- **Transaction boundaries**: one DB transaction per API request that writes more than one row — e.g. creating an invoice + its Activity Log entry + (if from a template) touching the template's usage is one transaction; the internal-ID sequencing read-then-insert (§Business Rule Placement) runs inside the same transaction at `SERIALIZABLE` (or `SELECT ... FOR UPDATE` on a per-property-year advisory lock) to prevent two concurrent invoice creations from racing to the same sequence number.
- **Error handling**: FK-violation (`23503`) and check-violation (`23514`) Postgres errors are caught at the repository boundary and translated to typed API errors (`ConflictError`, `ValidationError`) carrying the same meaning the app's current inline validation gives the user (e.g. "cannot delete property — invoices exist" from the new `invoices.property_id … RESTRICT` FK, worded identically to today's app-code message).
- **Activity Log handling**: every mutating repository call that changes a business record also inserts one `activity_logs` row in the same transaction (§Business Rule Placement) — implemented as a small repository-layer helper (`logActivity(tx, action, table, recordName, details, user)`) called explicitly at each mutation's call site, not a generic trigger-based audit (Postgres triggers can't easily capture the human `user_name`/free-text `details` semantics the current app writes), matching the "reproduced at the application layer" placement decision.
- **Authentication assumptions**: current app is effectively single-tenant/single-user (§14 — no Dataverse security-role-driven access control found). The API assumes the same for the migration itself: a single shared application credential (the `proptrack_app` Postgres role from `db/004_application_role.sql`) behind whatever front-door auth the API process itself enforces (e.g. a bearer token/session, TBD as a product decision, not re-litigated here) — no per-row Postgres RLS is designed in this step, since nothing in the current app requires it.
- **PostgreSQL connection management**: a single pooled `pg.Pool` (or equivalent) per API process, sized modestly (the whole dataset is 1,341 rows — this is not a high-concurrency workload), connecting as `proptrack_app` over the same NAS network path TripOrganiser/wealth-ledger already use, with `DATABASE_URL` supplied via environment variable (never committed — matching both sibling repos' `.env`/`.env.example` convention).

**Mapping of existing generated Dataverse operations → replacements**: every `src/generated/services/<Table>Service.ts` method (`create/retrieve/update/delete/retrieveMultiple`-shaped, per the `pac code add-data-source` convention) maps to the equivalent method on the new table repository; `src/data/dataverse/mappers.ts` (the layer that already translates Dataverse records ↔ `src/domain/` types, per `src/domain/types.ts`'s file header) is replaced by an equivalent `src/data/postgres/mappers.ts` translating API JSON ↔ the same `src/domain/` types — the **domain type shapes in `src/domain/types.ts` do not change**, only what populates them.

### 1. Schema — `db/007_document_storage.sql`

Extended `proptrack.attachments` (0 live records at the time this was applied — confirmed by

### 2. API — `api/src/documents/`, `api/src/routes/documentsRoutes.ts`

- **`api/src/documents/paths.ts`** — the single path-safety module every filesystem-touching
  route goes through. `DOCUMENTS_ROOT` is resolved (`path.resolve`) and canonicalized once at
  module load from the `DOCUMENTS_ROOT` env var (default `./data/documents` in `api/.env.example`;
  local dev default actually set to `./data/documents-dev`, gitignored). `resolveRelativePath()`
  rejects empty/`.`/`..` segments, control characters (including null bytes), backslashes, and
  absolute paths (POSIX and `C:`-style) with a `ValidationError` → HTTP `400` — never lets a bad
  path reach an `fs.*` call. `assertRealPathInsideRoot()` / `assertParentRealPathInsideRoot()`
  additionally re-verify via `fs.realpath` that the resolved path (or, for not-yet-created
  targets, its parent) doesn't escape the root through a symlink, satisfying the "actually verify
  with `fs.realpath`" instruction rather than relying on string-level checks alone.
- **`api/src/documents/config.ts`** — `MAX_UPLOAD_BYTES` (25MB default, overridable via
  `DOCUMENTS_MAX_UPLOAD_BYTES`) and an extensible MIME+extension allowlist covering PDF, JPG/JPEG,
  PNG, XLS, XLSX, DOC, DOCX (both the MIME type and the extension must match a pair — a spoofed
  Content-Type alone or a renamed-extension alone is rejected).
- **`api/src/routes/documentsRoutes.ts`**, mounted at `/documents` in `api/src/app.ts` **after**
  `app.use(requireToken)` — same auth gate as every other route, re-confirmed by reading
  `app.ts`'s router-mount order directly, not assumed:
  - `GET /documents/folders?path=` — lists subfolders/files under a validated path; a
    not-yet-created folder returns an empty listing rather than a 404 (browsing shouldn't require
    pre-creating folders); returns only `{path, name}` pairs, never a filesystem path.
  - `POST /documents/folders` — creates `<path>/<name>`, validated the same way.
  - `POST /documents/upload` — `multer` (memoryStorage — files are buffered, then written
    ourselves, so `paths.ts` alone decides where a file may land, not multer); validates the
    destination folder, the file's MIME+extension pair and size, generates a UUID-based
    `stored_filename` (collision-safe by construction — confirmed live, see §6), writes with
    `fs.writeFile(..., {flag:'wx'})` (fails rather than silently overwrites if the target somehow
    already exists), then creates the `attachments` row. **Consistency**: if the DB insert throws
    after the file write succeeded, the just-written file is deleted (`fs.unlink`, best-effort)
    before the error propagates — no orphaned file survives a failed metadata write; conversely a
    failed file write never reaches the DB-insert step at all (sequential, not parallel).
  - `GET /documents/:id` — looks up the row, 404s if no `storage_path` (i.e. it's a legacy
    Drive-only row — nothing to stream), re-validates the stored path via
    `assertRealPathInsideRoot` before streaming, sets `Content-Type` from the stored `mime_type`
    and `Content-Disposition: attachment; filename="<original_filename>"`.
  - `DELETE /documents/:id` — deletes the physical file then the metadata row. **Documented
    choice** for the missing-file case: if the file is already gone from disk (`ENOENT`), the
    metadata row is still deleted (an orphaned row pointing at nothing is worse than none), but
    the JSON response includes a `warning` field (`"Physical file was already missing on disk;
    removed metadata only."`) rather than silently reporting a clean delete — the caller can
    decide whether to surface that to the user. Verified live in §6/§8 below, not just by reading
    the code.
  - Move/rename was **not implemented** — skipped deliberately as the task's optional item, not
    silently dropped. Deleting and re-uploading is today's only path to relocate a document.

Root cause, confirmed by inspecting the actual import graph rather than guessing: `src/generated/services/*.ts`

- `vite.config.ts`'s `nasDataBackendPlugin` (new, active only when `VITE_DATA_BACKEND=postgres`)
  redirects every resolved `@/data` import to that file — required because Vite's own alias
  resolution runs before a plugin's `resolveId` sees the specifier (so the redirect matches on the
  already-expanded absolute path, not the literal `'@/data'` string — found by tracing real
  `resolveId` calls during a build, not assumed).
- `tsconfig.app.nas.json` (new) — extends `tsconfig.app.json`, adds a matching `paths` override
